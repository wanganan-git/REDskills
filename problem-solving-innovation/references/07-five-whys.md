# 5Whys 五问法

## 一句话定义
遇到问题连续追问五次"为什么"，穿透表象症状逐层深挖，直到找到根本原因而非止于表面解释。

## 核心原理与步骤

**原理：**
问题的表象和根因之间通常隔着3-5层因果关系。大多数人停在第一层"为什么"就急着给方案，结果治标不治本，问题反复出现。五问法强制你继续往下挖。

**操作步骤：**
1. **明确问题** — 用具体、可观察的语言描述问题（不要用模糊描述）
2. **问第一个为什么** — 为什么这个问题会发生？
3. **对答案再问为什么** — 逐层深挖
4. **持续追问直到根本原因** — 通常在第3-5层会到达"可以采取行动"的根因
5. **验证因果链** — 反过来检查：如果修了根因，上面每一层是否都会消失？

**追问原则：**
- 每一层答案必须是事实或可验证的因果关系，不能是猜测
- 如果某一层分叉出多个原因，对每个分支分别追问
- 追问到"可以采取具体改进行动"的层面就停
- 不一定要正好5次，3次到7次都正常

## 适用场景
- 故障排查（产品bug、设备故障、流程失效）
- 问题反复出现、修了又犯
- 需要区分"直接原因"和"根本原因"
- 事故复盘和归因分析
- 团队习惯性地"头痛医头"时，用五问法拉回系统思考

## 实操案例
**问题：** 线上服务突然宕机。

- **Why 1：** 为什么宕机？→ 服务器内存溢出
- **Why 2：** 为什么内存溢出？→ 某个API请求量激增导致内存占用飙升
- **Why 3：** 为什么请求量激增？→ 某营销活动带来10倍流量
- **Why 4：** 为什么营销活动没提前告知技术团队？→ 市场部和技术部没有上线前同步机制
- **Why 5：** 为什么没有同步机制？→ 公司没有跨部门协作的标准化流程

**根本原因：** 缺少跨部门协作流程（组织问题），不是服务器配置问题（技术问题）。

**如果只修第一层：** 加内存 → 下次活动还会崩
**修根本因：** 建立营销活动上线前的技术评审流程 → 所有类似问题不再发生

**另一个经典案例（丰田）：**
- 机器停了 → 为什么？→ 保险丝烧了
- 为什么烧了？→ 负荷过大
- 为什么过大？→ 轴承润滑不够
- 为什么不够？→ 油泵磨损
- 为什么磨损？→ 没有过滤网，金属屑进入

**根因：** 装过滤网（成本几块钱），而不是换保险丝（反复换）。

**关键洞察：** 五问法的难点不在于"问"，而在于"敢于质疑自己满意的答案"。很多时候第一层答案看起来很合理（"内存不够就加内存"），但它只是治标。真正的根因往往在流程、制度、认知层面。
